## File faults and independent interruption

Original source is the frozen 46-byte Y-01 YAML, edit n=2; existing destination
is ORIGINAL+LF. Parent snapshots capture prepared state, fault-active state,
immediate post-child state, and only then restoration/cleanup. No real config is
edited. The child first reads the actual input, parses, edits, serializes and
validates the full value. Safe replacement then creates a new sibling, writes
all bytes, syncs, closes, renames and rereads if reachable.

- Missing input: capture original fixture, remove it before invocation, expect
  actual read error under a valid narrow Deno grant.
- Unreadable input: chmod 000, retain inaccessible state/error, restore 0600 only
  after immediate aftermath and compare original bytes.
- Missing parent: target outputs/absent/replacement.tmp; absent parent remains
  absent and the separate existing destination remains unchanged.
- Unwritable parent: outputs/blocked contains the existing destination; chmod
  directory 0500 before operation and restore 0700 after aftermath.
- Raw/safe interruption: write exactly floor(serializedBytes/2) to the truncated
  raw destination or new safe sibling, sync that partial write, publish a
  checkpoint with child PID, path, full/partial sizes, hash and exact prefix,
  then wait in a synchronous loop. Supervisor verifies the PID in its observed
  child tree and independently rereads the actual partial bytes before kill.
  It snapshots the visible state before kill and immediate aftermath before
  deleting any orphan. Startup timeout is never counted as partial-write proof.
- Pre-rename injection: explicitly throw DECLARED_INJECTION_BEFORE_RENAME after
  complete sibling write/sync/close; retain orphan bytes, then separate cleanup.
- Rename over directory: actual destination is a directory containing
  DIRECTORY-SENTINEL+LF; exercise the real rename error and retain sentinel/temp.

Actual OS errors, Deno permission denials, deliberate injection and failure to
express the intended fault are separate. No atomicity, cross-platform,
concurrency, ownership or power-loss durability claim follows; Slice04 owns
those policy questions.
