# Deno Runtime Basics

The foundational Deno reference for lykn projects: security model,
permissions, namespace APIs, Web Platform APIs, configuration, module
resolution, and the standard library. lykn compiles to Deno-native ESM,
so all Deno runtime features apply to compiled output.

This is a condensed reference. For the full treatment of each topic,
see the JS guide `12-deno/12-01-runtime-basics.md`.

Target environment: **Deno**, **ESM-only**, lykn/surface syntax throughout.
For normal project work, use the lykn CLI wrappers (`lykn build`, `lykn run`,
`lykn test`, `lykn lint`). Direct `deno` commands in this guide teach Deno
runtime mechanics such as permissions and APIs.

---

## Security & Permissions

### ID-01: Deno Is Secure by Default

**Strength**: MUST

Deno checks protected operations such as file reads/writes and network access.
`lykn run` adds no permission grants: the launched program uses Deno's normal
permission policy, including interactive prompts when available. Use explicit
scopes for the access the program needs and `--no-prompt` to fail on missing
permissions without a prompt. These flags apply to runtime access, not the
compiler reading source or emitting JavaScript.

```sh
# Compile and run with explicit runtime permissions
lykn run --no-prompt --allow-net=api.example.com --allow-read=./data packages/server/mod.lykn

# All permissions require an explicit request
lykn run -A packages/server/mod.lykn
```

### ID-02: Use Granular Permissions

**Strength**: SHOULD

Scope permissions to specific paths, hosts, and variables.

```sh
lykn run --no-prompt \
  --allow-read=./config,./data \
  --allow-write=./output \
  --allow-net=api.example.com:443 \
  --allow-env=PORT,DATABASE_URL \
  packages/server/mod.lykn
```

### ID-03: Permission Prompts for Interactive Use

**Strength**: CONSIDER

Without `--no-prompt`, Deno retains its ordinary interactive prompting policy.
For unattended checks, `lykn run --no-prompt FILE` fails when a protected
operation needs a permission that was not granted. For example, a program that
reads `./data/input.json` fails under that command and can succeed with
`lykn run --no-prompt --allow-read=./data FILE`.

Runtime options must appear before FILE. In `lykn run FILE -- --allow-read`,
`--allow-read` is a program argument and grants nothing. Scoped optional values
require `=`, for example `--allow-read="./input data"`; repeated scoped flags
accumulate. See `../15-lykn-cli.md` for the complete option and separator contract.

### ID-04: Deny Flags for Exclusion

**Strength**: CONSIDER

`--deny-net=evil.com` blocks specific resources within broader grants.
For files, `lykn run --no-prompt --allow-read=./data --deny-read=./data/private FILE`
permits reads under `./data` except the denied subtree. Both allow and deny flags
support `read`, `write`, `net`, `env`, `run`, `sys`, `ffi`, and `import`; use bare
flags only when the whole category is intended.

## Core APIs

### ID-05: File I/O — `Deno:readTextFile` / `Deno:writeTextFile`

```lykn
(bind text (await (Deno:readTextFile "./config.json")))
(await (Deno:writeTextFile "./output.json" (JSON:stringify data)))
```

### ID-06: HTTP Server — `Deno:serve`

```lykn
(Deno:serve (obj :port 8080) (fn (:any req)
  (new Response "Hello from lykn!")))
```

### ID-07: Subprocess — `Deno:Command`

```lykn
(bind cmd (new Deno:Command "lykn"
  (obj :args #a("lint" "packages/myapp"))))
(bind output (await (cmd:output)))
```

### ID-08: Environment — `Deno:env:get`

```lykn
(bind port (Number (?? (Deno:env:get "PORT") "8080")))
```

### ID-09: CLI Arguments — `Deno:args`

```lykn
(bind args Deno:args)
```

## Module Resolution

### ID-10: ESM Only — Extensions Required

```lykn
(import "./utils.js" (transform))       ;; explicit .js extension
(import "@std/path" (join))              ;; import map specifier
```

### ID-12: `import:meta` for Module Metadata

```lykn
(bind dir import:meta:dirname)
(bind file import:meta:filename)
(bind url import:meta:url)
```

## lykn-Specific: The Compilation Step

### ID-16: lykn → JS → Deno Pipeline

lykn source compiles to JavaScript before Deno runs it. For normal project
workflows, use the lykn CLI wrappers instead of hand-managing generated JS.

```sh
# Build workspace packages
lykn build

# Run a lykn entry point
lykn run packages/myapp/main.lykn

# Test lykn tests; compiled JS lands under target/lykn/test/
lykn test

# Lint lykn source
lykn lint packages/myapp/
```

`lykn build` writes intermediate `.js` output to `target/lykn/build/`.
`lykn test` compiles `.lykn` and `.lyk` tests into `target/lykn/test/` before
invoking Deno's test runner. Deno permissions, APIs, and configuration apply
when the compiled `.js` runs; the project workflow should still start from the
lykn wrappers.
