# Mycelium Bootstrap: Issues Encountered

Report from the first real downstream project built with the lykn toolchain
(mycelium, April 2026). Every issue below was encountered during the
implementation of `@lykn/mycl` and `@lykn/mycl-html`.

---

## 1. `?` suffix in function names produces invalid JavaScript

**What happened:** `(func void-element? ...)` compiled to
`function voidElement?(tag)` and `import {voidElement?}` — the `?` is
not a valid character in JS identifiers. The compiled output fails to
parse.

**Workaround:** Renamed to `is-void-element`.

**Impact:** Any lykn function using the `?` predicate naming convention
(documented in the SKILL guide, core idioms ID-17, API design ID-17)
produces broken JS.

**Recommendation:**
- **File a bug** against `oxur/lykn`: "Function names with `?` suffix
  compile to invalid JS identifiers."
- **Fix in the compiler:** Map `?` to a valid JS suffix. Options:
  `_QMARK_` (ClojureScript convention), `$q` (short), or `_p`
  (predicate, Scheme convention). The choice should be documented in
  the surface forms reference.
- **Update guide `00-lykn-surface-forms.md`:** Add a note under the
  naming conventions table explaining how `?` compiles and any
  limitations.
- **Update guide `09-anti-patterns.md`:** Add a lykn-specific entry
  warning about `?` until the compiler fix ships.

## 2. `import-macros` cannot resolve `jsr:` or `npm:` specifiers

**What happened:** Test files using
`(import-macros "jsr:@lykn/testing" ...)` throw at runtime:
```
Error: import-macros: resolved jsr:@lykn/testing to non-file URL
```
The macro expander's `resolveImportMacrosSpecifier` requires a
`file://` URL but Deno's import map resolves registry specifiers to
non-file URLs. Bare names in the import map that point to `jsr:` or
`npm:` values fail the same way.

**Workaround:** Point the import map at a local filesystem checkout of
the lykn repo:
```json
"testing": "../lang/packages/testing/",
"testing/": "../lang/packages/testing/"
```
This is not viable for published packages, CI without a sibling
checkout, or downstream users installing via `deno add`.

**Impact:** Any project outside the lykn monorepo cannot use
`import-macros` with published macro packages. The three-tier
resolution scheme documented in DD-34 is effectively broken for
tiers 1 (scheme-prefixed) and 2 (bare names mapping to registries).

**Recommendation:**
- **File a bug** against `oxur/lykn`: "`import-macros` fails for
  `jsr:` and `npm:` specifiers — only filesystem paths work."
  (Detailed write-up already in
  `workbench/bug-import-macros-jsr-resolution.md`.)
- **Fix in the compiler:** Resolve registry specifiers to Deno's
  local cache path (via `deno info --json`), or ensure published
  macro packages ship `.lykn` source and the resolver can find it
  in `node_modules/` or the Deno cache.
- **Update guide `16-testing.md`:** Add a "Using @lykn/testing in
  external projects" section documenting the current limitation and
  the local-path workaround.

## 3. `lykn new` scaffolds a project that cannot publish to JSR

**What happened:** The `lykn new mycelium` scaffold generated:
- A `project.json` workspace config
- A `packages/mycelium/deno.json` without a `license` field
- A `.gitignore` that ignores compiled `.js` output

Both of these cause JSR publish to fail:
- **Missing license:** `error[missing-license]: missing license field or file`
- **Gitignored exports:** `error[excluded-module]: module in package's
  module graph was excluded from publishing` — JSR treats gitignored
  files as excluded from the published package.

**Workaround:** Added `"license": "Apache-2.0"` to each package
`deno.json` manually. Removed the `.js` gitignore patterns.

**Impact:** Every `lykn new` project will hit these errors on first
JSR publish attempt.

**Recommendation:**
- **Fix in the CLI** (`lykn new`):
  - Add `"license": "Apache-2.0"` (or prompt for it) to the
    generated `deno.json`.
  - Do not gitignore compiled `.js` output in the generated
    `.gitignore`, or add a comment explaining the JSR trade-off.
- **Update guide `15-lykn-cli.md`:** Document the JSR publish
  requirements (`license` field, no gitignoring of exported modules).
- **Update guide `10-project-structure.md`:** Add a note about
  the gitignore/JSR interaction under ID-03 (reference directory
  structure) or ID-26 (compilation pipeline).

## 4. CORRECTED: `package.json` and `jsr.json` are generated by `lykn build --dist`

**What happened:** I hand-wrote `package.json` and `jsr.json` for each
package, not realizing that `lykn build --dist` generates them
automatically in `dist/`. This was a discoverability failure, not a
toolchain gap — the CLI docs (`15-lykn-cli.md` ID-04d, ID-04e) describe
this clearly, but the SKILL.md workflows never mention publishing, so
I never reached those docs.

**Root cause:** The SKILL.md Document Selection Guide has no
"Publishing" row, and the Workflows section has no publishing workflow.
The "Writing New lykn Code" workflow ends at `lykn compile` without
connecting to the publish pipeline.

**Recommendation:**
- **Update SKILL.md:** Add a "Publishing a package" row to the
  Document Selection Guide and a "Publishing a Package" workflow.
- **Update guide `10-project-structure.md`:** Show `dist/` in the
  reference layout and note that `package.json`/`jsr.json` are
  generated — do not hand-write them.
- See `workbench/proposed-skill-and-guide-additions.md` items 1, 2,
  and 5 for the full proposed text.

## 5. Nested `if` chains in `func` body produce invalid JS

**What happened:** A `func` body with nested `if` used as the return
expression:
```lykn
(func render-node
  :args (:any node) :returns :string
  :body
  (if (js:eq node null) ""
    (if (= (js:typeof node) "string") (escape-text node)
      (if ...))))
```
Compiled to a mix of ternary and `if` statements in expression
position:
```js
const result = node == null ? "" : if (typeof node === "string") ...
```
This is a JS syntax error — `if` statements cannot appear in
expression position.

**Workaround:** Restructured as guard clauses with explicit `return`:
```lykn
(if (js:eq node null) (return ""))
(if (= (js:typeof node) "string") (return (escape-text node)))
...
(last-expression)
```

**Impact:** Any `func` that needs multi-branch type dispatch as its
return expression will hit this. The pattern is common in renderers,
parsers, and serializers.

**Recommendation:**
- **File a bug** against `oxur/lykn`: "Nested `if` in `func` `:body`
  return position produces mixed ternary/statement output."
- **Investigate in the compiler:** The surface compiler should
  consistently compile `(if test then else)` as a ternary when it
  appears in expression position (the last expression of a `func`
  body). Currently it seems to use ternary for `js:eq` conditions
  and `if` statements for `=` conditions.
- **Update guide `01-core-idioms.md`:** Add an idiom (or note under
  ID-26, early returns) documenting the guard-clause pattern as the
  recommended approach for multi-branch dispatch in `func` bodies.
- **Update guide `09-anti-patterns.md`:** Add an entry warning
  against deeply nested `if` chains as `func` return expressions.

## 6. `(express cell):method` chaining produces wrong output (ID-31)

**What happened:** `((express parts):join "")` compiled to
`parts.value("join", "")` — a function call passing `"join"` as an
argument, not a method call on the expressed value.

**Workaround:** Intermediate binding:
```lykn
(bind result (express parts))
(result:join "")
```

**Impact:** This is already documented as ID-31 in `01-core-idioms.md`
but is easy to hit in practice. The error is silent — no exception, just
wrong behavior.

**Recommendation:**
- **No new bug needed** — ID-31 is documented.
- **Consider a compiler fix:** Detect `(express x)` in method-call
  head position and emit correct code, or emit a compile-time warning.
- **Update guide `09-anti-patterns.md`:** Add a lykn-specific entry
  cross-referencing ID-31. The current anti-patterns guide doesn't
  mention this trap.

## 7. `?` (ternary) vs `if` confusion for conditional bindings

**What happened:** `(bind x (if cond a b))` compiled to
`const x = if (cond) a; else b;` — an `if` statement in assignment
position, which is invalid JS.

**Workaround:** Use `?` (the ternary form):
`(bind x (? cond a b))` → `const x = cond ? a : b;`

**Impact:** The surface forms reference lists `if` under "Control Flow
(kernel forms)" and `?` under expressions, but this distinction is
subtle. Developers coming from Lisp expect `if` to be an expression.

**Recommendation:**
- **Update guide `00-lykn-surface-forms.md`:** Add a prominent note
  under `if` clarifying that it is a **statement** form. For
  conditional expressions in binding position, use `?`.
- **Update guide `01-core-idioms.md`:** Add an idiom: "Use `?` for
  conditional bindings, `if` for conditional side effects."
- **Update guide `09-anti-patterns.md`:** Add an entry: "Using `if`
  in expression/binding position — use `?` instead."
- **Consider a compiler warning:** When `if` appears as the
  initializer of `bind`, emit a warning suggesting `?`.

## 8. JSR publish requires `--allow-slow-types` for JS entrypoints

**What happened:** `deno publish` failed with
`warning[unsupported-javascript-entrypoint]` because the compiled
`.js` entrypoint has no `.d.ts` type declarations. JSR's fast-check
requires either TypeScript source or declaration files.

**Workaround:** Pass `--allow-slow-types` to `deno publish`.

**Impact:** Every lykn package published to JSR will need this flag
until lykn generates `.d.ts` files alongside `.js` output.

**Recommendation:**
- **File a feature request** against `oxur/lykn`: "Generate `.d.ts`
  declaration files from `func` type annotations during compilation."
  This would leverage lykn's built-in type annotations (`:number`,
  `:string`, `:returns`, etc.) to produce TypeScript declarations
  automatically.
- **Update guide `15-lykn-cli.md`:** Document that JSR publish
  requires `--allow-slow-types` for lykn-compiled JS output.
- **Update `lykn publish --jsr`:** If the CLI wraps `deno publish`,
  pass `--allow-slow-types` by default (or until `.d.ts` generation
  is implemented).

## 9. `lykn new` project.json missing `lang/` and `testing/` imports

**What happened:** `lykn test` internally uses the JS-based compiler
(`lang/` package) to compile `.lykn` test files. The generated
`project.json` does not include the `lang/` or `testing/` import map
entries needed for `lykn test` to work.

In the lykn monorepo, these resolve to local paths
(`./packages/lang/`, `./packages/testing/`). In external projects,
they don't resolve at all — `lykn test` fails with:
```
error: Import "lang/mod.js" not a dependency and not in import map
```

**Workaround:** Manually added to `project.json`:
```json
"lang/": "../lang/packages/lang/",
"testing": "../lang/packages/testing/",
"testing/": "../lang/packages/testing/",
"astring": "npm:astring@^1.9.0"
```

**Impact:** `lykn test` does not work out of the box in any project
created with `lykn new`. This is closely related to issue #2
(import-macros JSR resolution) but is a separate problem — the CLI
itself needs the compiler modules, independent of macro resolution.

**Recommendation:**
- **File a bug** against `oxur/lykn`: "`lykn test` fails outside
  the lykn monorepo — missing `lang/` import map entry."
- **Fix in the CLI:** Either bundle the JS compiler into the Rust
  binary (so it doesn't need external resolution), or have `lykn new`
  generate the correct import map entries for the installed lykn
  version.
- **Fix in `lykn new`:** Generate the `astring`, `lang/`, and
  `testing/` imports in `project.json` pointing to the published
  packages.

## 10. npm EOTP error with Automation token

**What happened:** `npm publish` returned `EOTP` (one-time password
required) even though an Automation token was configured in `.npmrc`.
Automation tokens are specifically designed to bypass 2FA.

**Workaround:** Under investigation — likely a token type or scoping
issue on the npm side, not a toolchain bug.

**Impact:** Blocks npm publishing from the command line and from CI.

**Recommendation:**
- **Verify token type** at npmjs.com → Access Tokens. The type column
  must say "automation", not "publish".
- **Add to Makefile publish docs:** A comment noting that EOTP with
  an Automation token means the token type is wrong.
- **No lykn toolchain change needed** — this is an npm configuration
  issue.

## 11. Compiler warns about "unused bindings" that are used

**What happened:** `lykn compile` emitted false-positive warnings:
```
warning: unused binding 'VOID-ELEMENTS'
warning: unused binding 'TAG-RE'
warning: unused binding 'render-element'
```
All three bindings are used — `VOID-ELEMENTS` is referenced via
`VOID-ELEMENTS:has` inside `is-void-element`, `TAG-RE` is used in
`validate-tag`, and `render-element` is called from `render-node`.

**Workaround:** Ignored the warnings. They don't affect compilation.

**Impact:** Noisy compiler output. Developers may start ignoring
all warnings, including real ones.

**Recommendation:**
- **File a bug** against `oxur/lykn`: "Unused binding checker
  produces false positives for bindings used inside function bodies."
- **Fix in the compiler:** The unused-binding analysis should track
  references inside `func`/`fn` bodies, not just top-level
  references.

## 12. Makefile used raw `npm publish` / `deno publish` instead of `lykn publish`

**What happened:** The Makefile publish targets called `npm publish`
and `deno publish` directly, with ~120 lines of shell handling OTP
flags, already-published detection, error routing, and manual `cd`
into `dist/` directories. Meanwhile, `lykn publish --npm` and
`lykn publish --jsr` wrap all of this — including `lykn build --dist`
— in a single CLI command.

The no-Node boundary guide (`14-no-node-boundary.md` ID-07) says
`npm install` / `npm run` are MUST-AVOID. While it doesn't explicitly
list `npm publish`, the principle applies: use lykn's wrappers, not
raw npm/deno commands.

**Root cause:** Same as issue #4 — the SKILL.md workflows don't
mention publishing, so the `lykn publish` command was never
discovered during implementation. The lykn Makefile itself uses
`lykn publish --jsr` and `lykn publish --npm`, but this wasn't
checked as a reference until late in the process.

**Recommendation:**
- Covered by the same SKILL.md additions proposed in issue #4
  (publishing workflow, document selection guide row).
- **Update guide `14-no-node-boundary.md`:** Add `npm publish` to
  the MUST-AVOID table with `lykn publish --npm` as the replacement.

## 13. Confusing config file naming: `project.json` vs `deno.json`

**What happened:** The lykn convention is `project.json` at the
workspace root and `deno.json` at the per-package level. This naming
doesn't signal the hierarchy — both are opaque JSON files whose
relationship only becomes clear after reading the guides.

During the mycelium bootstrap, the distinction was confusing: the
workspace root needed `project.json` (not `deno.json`), and each
package needed `deno.json` (not `project.json`). Nothing in the names
tells you which is which. A developer encountering the project for the
first time has to already know the convention.

**Impact:** Cognitive overhead and easy to mix up. The names don't
carry meaning about their role in the workspace/package hierarchy.

**Recommendation:**

- **Consider renaming** in a future lykn version:
  - Workspace root: `workspace.json` (currently `project.json`)
  - Per-package: `package.json` (currently `deno.json`)

  This makes the hierarchy self-documenting: `workspace.json` contains
  workspace members, `package.json` contains package metadata. The
  names describe what they configure.

- **Conflict with npm:** `package.json` is already used by npm. Since
  `lykn build --dist` generates a separate npm `package.json` in
  `dist/`, there may not be a conflict — the source `package.json`
  would be lykn's config, and the dist `package.json` would be npm's.
  But this needs careful design to avoid confusion.

- **Alternative:** Keep `project.json` at the root but rename the
  per-package file to `package.json` or `lykn.json` — anything that
  distinguishes it from the workspace config.

- **At minimum:** Update guide `10-project-structure.md` to explicitly
  name the two files side-by-side and explain the distinction. The
  current guide mentions both but doesn't contrast them or explain
  why one is `project.json` and the other is `deno.json`.

## 14. Compiled `.js` output pollutes source directories

**What happened:** `lykn compile foo.lykn -o foo.js` writes the
compiled output alongside the source file. During development, every
`make build` deposits `.js` files next to `.lykn` files in the
package directories. These compiled artifacts then show up in
`git status`, must be committed (because JSR treats gitignored files
as excluded modules), and mix source-of-truth `.lykn` files with
generated `.js` output in the same directory listing.

This is the same problem Rust solved with `target/` — compiled
artifacts go to a dedicated output directory, keeping the source tree
clean. C projects have `build/`. Go has its module cache. lykn
currently has no equivalent separation.

**Consequences:**

- Source and generated files are interleaved in directory listings,
  making it harder to see what's authored vs what's derived.
- `git status` always shows `.js` changes after a build, even when
  no source changed (e.g., compiler version bump changes output
  formatting).
- `.gitignore` is in tension with JSR: ignoring `.js` files keeps the
  tree clean but breaks `deno publish`; committing them clutters the
  repo with generated code.
- `make clean` must know exactly which `.js` files are generated vs
  hand-written (currently uses `find packages -name '*.js' -delete`
  which would also delete any hand-written JS helpers).

**Recommendation:**

- **Design a `target/` or `out/` directory** for lykn compilation
  output, analogous to Rust's `target/` directory:

  ```
  my-project/
  ├── packages/
  │   └── my-lib/
  │       ├── deno.json
  │       ├── mod.lykn          ← source (committed)
  │       └── render.lykn       ← source (committed)
  ├── target/                   ← compiled output (gitignored)
  │   └── my-lib/
  │       ├── mod.js            ← generated
  │       └── render.js         ← generated
  └── dist/                     ← publish-ready staging (gitignored)
      └── my-lib/
          ├── mod.js
          ├── package.json      ← generated by lykn build --dist
          └── deno.json         ← generated by lykn build --dist
  ```

- **Three-tier separation:**
  - `packages/` — source `.lykn` files only (committed)
  - `target/` — compiled `.js` for development and testing (gitignored)
  - `dist/` — publish-ready staging (gitignored, generated by
    `lykn build --dist`)

- **CLI changes needed:**
  - `lykn compile` default output goes to `target/<pkg>/` instead
    of in-place.
  - `lykn test` resolves imports against `target/` instead of
    expecting `.js` next to `.lykn`.
  - `lykn build --dist` continues to stage into `dist/` as today,
    but reads from `target/` instead of in-place `.js`.
  - `lykn run` compiles to `target/` and executes from there.

- **Immediate workaround:** The Makefile could compile to a `target/`
  directory today, but `lykn test` and import resolution would break
  because they expect `.js` files adjacent to `.lykn` source. This
  needs CLI-level support to work properly.

- **Update guide `10-project-structure.md`:** Add the three-tier
  model to the reference layout and explain the separation of
  concerns between source, compiled, and publish-ready artifacts.
