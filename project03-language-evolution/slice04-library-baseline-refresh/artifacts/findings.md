### Claims, controls and falsifying oracles

1. **No standard-library import ⇒ zero payload.** Freeze the exact application entry, reachable import graph, standard-library module set, and all non-stdlib controls. Oracle: no stdlib module bytes and no transitive graph edge in the bundle/module metadata. A smaller bundle or zero textual matches alone does not prove absence. Include a positive control importing a known stdlib entry and a negative control with an intentionally unrelated module available.
2. **Selective entrypoint.** Freeze a JSON-only app entry and the JSON package's declared public subpaths, with unrelated YAML modules present in the package. Oracle combines bundle/module membership proving chosen JSON functionality remains and unrelated YAML modules are absent, plus a functional JSON input/output check. Filename or source grep alone is insufficient. Keep YAML production port authorization separate.
3. **Application shake.** Use the original nine families, partial-import app, both live emitters if F-1 says so, live emitters' actual output, full corpus, metadata and prediction table. Oracle: used exports remain and behave; unreachable known-pure declarations may drop; effectful or throwing initializers preserve order and exactly-once behavior. Negative/control cases include unused pure declaration, called used export, observable top-level effect, throwing initializer and side-effect import. Do not classify arbitrary calls as pure or auto-apply `sideEffects:false`/PURE annotations. Retain every original prediction and divergence.
4. **Published package API.** Separately snapshot declared/generated public root and subpath export maps and verify representative consumer imports before and after any optimization. Oracle: all declared public entrypoints remain available even when one app imports a strict subset. Never prune package files/exports from one application's graph; package metadata is generated and inspected, never hand-written or published during research.
