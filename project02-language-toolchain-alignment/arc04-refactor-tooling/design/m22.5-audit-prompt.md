## What this audit exists to determine

M22 was supposed to migrate 27 surface forms out of
`packages/lang/surface.js`'s macro registration into the new
`packages/lang/surface-ast.js` + `packages/lang/classifier.js`
pipeline, per DD-37 step 3 and the 2026-05-17 "Option C"
architectural directive. M22's closing report claims the migration
is complete.

CDC review found the closing-report claims do not match the code:
the dispatch migration is substantively done, but the
implementation migration (where the form-emitting logic physically
lives) is partial. Multiple evasion patterns appear to have been
used during M22 — alias re-export, delegation back to the source
file, reimplementation in lieu of copying.

This audit's purpose is to produce a **function-by-function
ground-truth report** that Duncan and CDC can use to plan
remediation workstreams. The audit must be independent of CC's
M22 closing report claims — verify everything against the actual
code and the pre-M22 git state.

## Expected vs. actual — evaluation criteria

For each item (form or helper), your evaluation needs to answer:

### For a form `X`:

**Expected (per Option C directive):**
- `classifier.js` has a case in `classifySurfaceForm` that
  recognizes `X` and produces a typed AST node.
- `classifier.js` has a case in `emitSurfaceForm` that consumes
  the typed AST node AND produces the kernel SExpr **inline** —
  i.e., the implementation body lives in classifier.js.
- `surface.js` no longer registers `X` as a macro (no
  `registerMacro('X', ...)` or equivalent).
- `surface.js` no longer contains the implementation body for
  `X` (no exported function that classifier.js delegates to).

**Actual (what you find):**
- Where is the implementation body physically located? (file:line)
- Is the implementation inline in classifier.js (Option C —
  correct), or does classifier.js delegate via a function call to
  surface.js (Option A — compromised)?
- Is the implementation bytewise-identical to the pre-M22 version
  in `surface.js`, modulo import-path changes? Or does it differ
  substantively?

**Status codes (pick one):**
- `MOVED_EXACTLY_OPTION_C` — body in classifier.js, bytewise
  match to pre-M22 (modulo imports), no surface.js delegation.
- `MOVED_WITH_EDITS_OPTION_C` — body in classifier.js, but
  differs from pre-M22 in non-trivial ways (cite the diffs).
- `DELEGATED_VIA_CALL_OPTION_A` — body still in surface.js as
  exported function; classifier.js calls it. Status the
  function name (e.g., `emitMatchMacro`) and surface.js line
  range.
- `STILL_IN_SOURCE_NOT_MIGRATED` — form is still registered as a
  macro in surface.js's `registerSurfaceMacros`, not classified
  at all.
- `REIMPLEMENTED_DIVERGES` — body in classifier.js, but differs
  substantively from pre-M22 (suggests reimplementation, not
  copying). Quote both.
- `MISSING_ENTIRELY` — neither classified nor registered. No
  trace.

### For a helper `H`:

**Expected:**
- Body lives in `surface-helpers.js` (or another suitable shared
  module).
- `surface.js` no longer defines `H` (it imports from helpers
  module if it still needs `H`).
- `classifier.js` imports `H` from helpers module (not from
  surface.js).

**Actual:**
- Where is `H`'s body physically located?
- If in `surface-helpers.js`, is it defined there or re-exported
  via `export { H } from "./surface.js"`?
- Does anything still import `H` directly from `surface.js`?

**Status codes for helpers:**
- `MOVED_TO_HELPERS_FILE` — body actually defined in
  surface-helpers.js.
- `ALIASED_FROM_SOURCE` — `surface-helpers.js` re-exports via
  `export { H } from "./surface.js"`; body still in surface.js.
- `STILL_IN_SOURCE_DIRECT_IMPORT` — body in surface.js;
  consumers import directly from surface.js, no
  surface-helpers.js re-export at all.
- `RE_EXPORTED_FROM_THIRD_FILE` — body in some other file
  (e.g., expander.js, compiler.js); surface-helpers.js re-exports
  for convenience. (This is structurally legitimate but worth
  flagging if the directive named it for extraction.)
- `MISSING_ENTIRELY` — not present anywhere.
